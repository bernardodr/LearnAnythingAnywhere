Lesson 2 · System Design Interviews

From requirements to a contract

Seven minutes of the interview that turn your requirements into something you can build.

Your win today Given a set of functional requirements, you'll be able to list the core entities and write a clean REST API in about 7 minutes. These are steps 2 and 3 of the delivery framework.

Warm-up: recall from Lesson 1

Answer these from memory. They come from your Bitly critique. Spacing your recall out like this is what turns "I've seen it" into "I know it".

Step 2: core entities (~2 min)

Core entities are the things your system stores and passes around. You can find them by asking two questions:[1]

  • Who are the actors? These are the people or systems taking actions.
  • What nouns do the functional requirements need? Underline them.

Try it on the Bitly requirements from last time:

Users submit a long URL and receive a short URL
Users visiting a short URL are redirected to the original

That gives you Original URL, Short URL, and the actor, User.[2] Write them as a bullet list and move on. Don't write out fields or a schema yet. You don't know enough at this point, and the details will come out during the high-level design.[1]

Coming from Java? An entity is not a class hierarchy. Two minutes, a few nouns, clear names. Think of it as a glossary for the rest of the interview, not a domain model.

Step 3: the API (~5 min)

The API is the contract between your system and its users. The rule of thumb is one endpoint per functional requirement, which ties your design directly to what you agreed with the interviewer.

Four conventions that signal fluency

  1. Default to REST. Reach for GraphQL only when many different clients need different data. Use RPC (such as gRPC) for performance-critical internal calls.[1]
  2. Resources are plural nouns. Write /tweets, not /tweet or /createTweet. The HTTP verb carries the action.
  3. Use verbs the usual way. POST creates, GET reads, PUT/PATCH updates, DELETE removes.
  4. Get the user from the auth token in the request header. Never trust a userId in the body, because a client could put anyone's ID there.[1]

Bitly's API

// FR1: shorten a URL
POST /urls
body: {
  "long_url": "https://www.example.com/some/very/long/url",
  "custom_alias": "optional",
  "expiration_date": "optional"
}
-> { "short_url": "http://short.ly/abc123" }

// FR2: redirect
GET /{short_code}
-> HTTP 302 redirect to the original long URL

Adapted from Hello Interview's Bitly breakdown.[2]

Notice two things. There's no user_id in the body, because the token supplies it. And the optional fields from the requirements show up as optional fields in the request.

One detail worth saying out loud: 302, not 301

301 Moved Permanently tells browsers the move is permanent, and browsers usually cache it. 302 Found marks the move as temporary, so the browser comes back to your server each time.[3] A shortener usually wants 302. Expiry still works because the browser hasn't cached the target, and you keep control of every redirect. That control also enables click tracking later.[2] It's a small detail, but mentioning it shows interviewers you know how HTTP behaves.
